#
# ORDER AND PINNING MATTER, learned the hard way on this machine:
#   1. `pip install whisperx` RESOLVES TORCH ITSELF and will happily replace
#      a working CUDA build with a CPU one (observed: torch 2.8.0+cpu
#      silently overwriting cu121). That is the exact trap README §cuDNN
#      warns about, and `torch.cuda.is_available()` is the only proof.
#   2. Installing the newest CUDA torch afterwards then violates whisperx's
#      own `torch~=2.8.0` pin. So pin torch to the version whisperx wants,
#      from the CUDA index:
#        pip install "torch==2.8.0" "torchaudio==2.8.0" \
#            --index-url https://download.pytorch.org/whl/cu126
#      and re-check `clipforge doctor` afterwards.
#   3. TORCHVISION TOO — third occurrence of the CPU-wheel trap. A stray
#      `torchvision 0.23.0+cpu` next to CUDA torch makes every ultralytics
#      call die with "torchvision::nms ... not available for CUDA backend".
#      And `pip install torchvision==0.23.0 --index-url .../cu126` will NOT
#      fix it: pip treats the installed `+cpu` build as satisfying ==0.23.0
#      and skips it. Force the local tag explicitly:
#        pip install "torchvision==0.23.0+cu126" \
#            --index-url https://download.pytorch.org/whl/cu126 \
#            --force-reinstall --no-deps
#   4. ultralytics 8.4.x ships its own top-level `tests` package INTO
#      site-packages, shadowing this repo's tests/ for absolute imports.
#      Delete `<venv>/Lib/site-packages/tests` after installing; the root
#      conftest.py fails loudly if it comes back.
